# Database migrations

Forward-only, numbered, recorded in `wx_migrations`, and dry-runnable.

```bash
php db/migrate.php --status      # what is applied, what is pending
php db/migrate.php --dry-run     # print every statement, change nothing
php db/migrate.php               # apply pending migrations
php db/migrate.php --checksum    # apply, then report row-count changes per table
php db/migrate.php --verify      # CI: fail if anything is pending or an applied file changed
php db/migrate.php --only 003    # apply one migration (staged rollout)
```

## The files

| # | File | What it does | Plan reference |
|---|---|---|---|
| 000 | `000_platform.sql` | `wx_sessions`, `wx_secrets`, `wx_login_attempts`; adds `req_id`/`meta_json` to `wx_activity` | prerequisite for §6.3/§6.4 |
| 001 | `001_roles.sql` | **generated** — moves the capability matrix out of `roles-lib.php` into `wx_roles`, `wx_role_groups`, `wx_action_groups`, `wx_action_shared`, `wx_action_roles`, `wx_user_perms` | §9.2 DB-1 |
| 002 | `002_indexes.sql` | 12 composite indexes for the queries the screens run | §9.2 |
| 003 | `003_document_columns.sql` | real columns beside the JSON blobs (`quotes`, `invoices`, `projects`); `data` → `payload` | §9.2 |
| 004 | `004_fk.sql` | 10 foreign keys, each preceded by an orphan cleanup | §9.2 |
| 005 | `005_settings_seed.sql` | attention thresholds, site identity, permission-group labels | §9.2 |

`000` exists because the platform tables are a prerequisite of Phase 1 rather than part of the
schema programme the plan numbered 001–010; giving them their own file keeps 001–005 at exactly the
scope the plan promised.

## Two generated files

`001_roles.sql` is generated by `node tools/gen-caps.mjs` from `frontend-v1/api/roles-lib.php` — the
file v2.1 actually enforces. The seed rows are therefore provably the rules that were running, not a
transcription of them:

```bash
node tools/gen-caps.mjs           # regenerate
node tools/gen-caps.mjs --check   # CI: fail if the SQL and roles-lib.php have diverged
```

`api/v2/aliases.php` works the same way from the v2.1 dispatcher
(`node tools/gen-aliases.mjs --check`).

## Rules for writing a new migration

1. **Never edit an applied file.** The runner records a sha256 of each file and refuses to continue
   if a recorded migration has changed — a "fixed" migration is how two databases silently diverge.
   Add `006_…` instead.
2. **Every statement must be safe to repeat.** MySQL implicitly commits around DDL, so a transaction
   is not available as a safety net. Use `CREATE TABLE IF NOT EXISTS`, and guard `ALTER TABLE`
   through `information_schema` the way 002–004 do:

   ```sql
   SET @sql = (SELECT IF(COUNT(*) = 0, 'ALTER TABLE t ADD COLUMN c INT NULL', 'DO 0')
     FROM information_schema.columns
     WHERE table_schema = DATABASE() AND table_name = 't' AND column_name = 'c');
   PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
   ```
3. **One statement ends at `;\n`.** The splitter is line-based (it strips `--` comments and blank
   lines first), so keep semicolons that end a statement at the end of a line.
4. **Never drop a column in the same release that stops writing to it.** Stop writing first, verify on
   a restored copy, then drop in a later migration.
5. **Seeds never overwrite operator values.** `INSERT IGNORE` for settings, so a tuned threshold
   survives a re-run.
6. **Test on a restored copy first**, then compare row counts (`--checksum` prints them).

## Money

Totals in migration 003 are `BIGINT` **paisa** (1/100 rupee), matching `wx_v_money()` in the
validation layer. An integer is exact, sorts correctly, and cannot be mistaken for rupees by a client
that forgets the scale — which is precisely what happened in v2.1, where the totals lived inside
JSON and each screen did its own rounding.
